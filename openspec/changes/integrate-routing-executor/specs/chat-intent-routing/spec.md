## Purpose

为聊天请求提供统一、可追踪且与用户权限绑定的意图判断，使不同类型的问题进入明确的业务执行路径，避免依赖分散关键词逻辑产生不一致行为。

## ADDED Requirements

### Requirement: 统一意图分类

系统 SHALL 在创建聊天 Run 后、执行任何模型或业务工具前，对经过 Trim 的用户输入执行一次统一分类，并产生一个包含业务意图、任务复杂度、置信度、原因以及是否需要 RAG/模型的路由决策。业务意图与任务复杂度 MUST 是两个独立维度。

#### Scenario: 分类普通聊天

- **WHEN** 用户输入不包含笔记操作或复杂任务信号
- **THEN** 系统将业务意图标记为 `chat`、复杂度标记为 `simple`，并允许进入普通模型执行器

#### Scenario: 分类历史笔记查询

- **WHEN** 用户询问之前的记录、历史笔记或曾经提到的内容
- **THEN** 系统将业务意图标记为 `note.query`，并要求进入受保护的 RAG 执行器

#### Scenario: 分类明确笔记写入

- **WHEN** 用户明确表达“记一笔/保存笔记/帮我记住”
- **THEN** 系统将业务意图标记为 `note.create`，并禁止把该请求当作普通闲聊

#### Scenario: 分类复杂任务

- **WHEN** 输入达到复杂度阈值或包含分析、比较、综合、制定方案等复杂任务信号
- **THEN** 系统将复杂度标记为 `complex`，同时保留已识别的业务意图

#### Scenario: 分类复杂的历史笔记问题

- **WHEN** 用户要求综合分析或比较多条历史笔记
- **THEN** 系统将业务意图标记为 `note.query`、复杂度标记为 `complex`，并选择复杂笔记问答执行器

#### Scenario: 分类无法理解的输入

- **WHEN** 输入为空、缺少必要信息或无法满足任何有效路由条件
- **THEN** 系统将意图标记为 `intent.unclear`，并要求返回澄清请求

#### Scenario: 分类聊天删除请求

- **WHEN** 用户在聊天中要求删除笔记或删除记录
- **THEN** 系统识别为受限的 `note.delete` 业务意图，以便执行器明确拒绝，不得降级为普通聊天或调用删除能力

#### Scenario: 处理低置信度决策

- **WHEN** 写操作的分类置信度低于配置阈值
- **THEN** 系统转入澄清而不执行写入；只读聊天和查询可以按安全默认路径继续，并记录低置信度指标

### Requirement: 路由决策可观测且不可越权

系统 SHALL 将路由决策与当前 Run、用户和租户关联记录为内部事件；路由过程 MUST 使用已认证的用户上下文，且不得因为用户输入中的用户标识、知识库标识或工具参数改变权限范围。

#### Scenario: 记录路由事件

- **WHEN** 分类完成
- **THEN** 系统持久化 `route.decided` 事件，至少包含业务意图、复杂度、置信度、原因、是否需要 RAG 和是否需要模型

#### Scenario: 未认证请求分类

- **WHEN** 请求未通过 Agent Session 认证
- **THEN** 系统在分类和创建 Run 前返回未认证错误，且不写入路由事件
