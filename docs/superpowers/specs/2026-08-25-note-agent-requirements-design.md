# 笔记 Agent 需求范围设计

日期：2026-08-25  
状态：已完成对话设计确认，待书面规格审阅

## 1. 背景

本项目已有个人认证、笔记事实存储、RAG 检索、聊天、长期记忆、提醒、每日回顾与最小 Web 工作台。本设计不从现有实现简单反推产品，而是结合 flomo、Notion AI、Capacities 等产品的优势，重新定义个人笔记 Agent 的需求边界。

竞品启示如下：

- flomo 的核心优势是低摩擦输入、多级标签与主动回顾。
- Notion AI 将会议和文档内容进一步转化为可执行行动。
- Capacities 强调每日记录、知识关联与受控的 AI 读写。
- 本产品的差异化重点是：在低摩擦记录之上，提供有证据、可确认、可追溯的个人知识 Agent。

参考：

- [flomo 微信输入](https://help.flomoapp.com/basic/wechat-input.html)
- [flomo 多级标签](https://help.flomoapp.com/basic/tag.html)
- [flomo 每日回顾](https://help.flomoapp.com/advance/lucky.html)
- [Notion AI Meeting Notes](https://www.notion.com/en-US/product/ai-meeting-notes)
- [Capacities 产品能力](https://capacities.io/product)

## 2. 产品定位

产品面向个人用户与知识工作者，首版优先服务知识工作者。产品不要求用户先掌握复杂的知识管理方法，而是通过以下闭环降低记录、理解和行动成本：

> 记录 → 理解 → 行动 → 回顾 → 回流为新记录

四项贯穿原则：

1. **可信**：回答有来源，用户原文、AI 派生内容和外部资料明确区分。
2. **可控**：低风险整理可以自动执行，高风险写入必须确认。
3. **可追溯**：版本、来源笔记、任务、记忆与回顾结果之间保留关系。
4. **低负担**：使用时间流与多级标签，不引入空间树、对象系统或团队治理。

## 3. 目标与非目标

### 3.1 目标

- 用户可通过 Web 和微信快速记录文字、图片、文件和链接。
- 系统自动完成不改变用户原意的低风险整理。
- 用户可基于个人笔记进行带来源的问答和主动洞察。
- 用户可在明确要求时，让 Agent 结合外部知识回答。
- 笔记中的行动可经确认转化为轻量任务。
- 用户可主动发起每日回顾、每周回顾和往日回声。
- 微信对话支持任务创建和三层记忆管理。
- 所有事实写入、确认和状态变化具备权限、版本、幂等与审计边界。

### 3.2 首版非目标

- 原生 iOS、Android 或桌面客户端。
- 浏览器扩展和 PWA 专项能力。
- 会议录音与自动转写。
- 提醒通知、定时投递、重复提醒或日历同步。
- 完整项目管理、负责人协作或外部应用写入。
- 空间、文件夹、复杂知识对象和关系建模。
- 分享、团队知识库、协同编辑和成员权限。
- 自动调度回顾或主动推送往日回声。
- 模型自行激活长期记忆或执行不可逆写入。

仓库内已有 Reminder 能力可以保留，但不属于本次产品主闭环。

## 4. 核心用户旅程

### 4.1 记录

用户从 Web 或微信提交内容。系统先保存原始输入，再异步执行解析、OCR、索引和 AI 整理。用户无需在记录时选择分类结构。

### 4.2 理解

用户通过知识对话询问个人笔记，或在阅读笔记时主动点击“洞察”。默认只使用个人笔记；只有用户明确提出结合外部资料时，系统才读取外部知识。

### 4.3 行动

Agent 从笔记或对话中识别行动候选。候选经用户确认后成为任务；用户也可在任务中心手动创建任务。

### 4.4 回顾

用户主动发起每日回顾、每周回顾或往日回声。报告默认只读，用户可确认保存为新笔记，或将其中行动项创建为任务。

## 5. 信息架构

Web 工作台提供五个一级入口：

1. **收集箱**：汇集 Web、微信和导入内容，展示处理状态、失败项和待确认内容。
2. **全部笔记**：提供时间流、多级标签、搜索、筛选、版本历史和单笔记洞察。
3. **知识对话**：提供个人笔记问答、引用展示和显式外部知识补充。
4. **任务**：展示行动候选与已确认任务，支持状态、截止日期和来源追溯。
5. **回顾**：提供每日回顾、每周回顾和往日回声的主动触发入口。

Agent 是贯穿以上入口的能力，不单独设置复杂的 AI 中心。

统一对象关系：

> 输入来源 → 笔记及版本 → 洞察或回答引用 → 任务 → 回顾报告 → 新笔记或新任务

对话本身不是笔记或任务的事实来源；只有经用户确认保存的结果才成为正式业务对象。

## 6. 第一阶段：记录

### 6.1 渠道与输入

首版渠道：

- Web 页面：完整记录和管理入口。
- 微信快捷输入：轻量记录与 Agent 对话入口。

Web 至少支持：

- 文字与 Markdown。
- PDF、纯文本和 Markdown 文件。
- JPEG、PNG 等常用图片格式。
- 网页链接。

微信至少支持：

- 文字。
- 图片。
- 网页链接。
- 任务创建和记忆管理对话。

不受支持的文件类型不得导致输入丢失；系统应保留原文件并明确提示当前不能提取正文。

### 6.2 笔记形态

- 快速记录默认形成卡片式 Memo，标题可选。
- 用户可继续编辑，将 Memo 扩展成长笔记。
- 文件、图片和链接导入形成一条笔记，并保留原始附件与来源。
- 短 Memo 与长笔记使用统一的搜索、关联、问答和回顾能力。

### 6.3 组织方式

- 用户只使用多级标签主动组织内容，例如 `#工作/搜索项目`。
- 不提供空间、文件夹、项目树和复杂对象类型。
- AI 可生成明确标记的 AI 标签。
- 用户可修改、删除 AI 标签，或将其转为手动标签。
- AI 主题聚类属于派生视图，不成为强制组织结构。

### 6.4 低风险自动整理

系统可自动执行：

- 文件解析、OCR 和网页正文提取。
- 搜索索引。
- 标题生成。
- 内容类型识别。
- AI 标签。
- 弱关联和相关内容建议。
- 行动候选识别。

自动整理结果必须标注为 AI 生成，可修改、撤销并查看处理状态。自动整理不得覆盖用户原文。

以下操作必须确认：

- 应用 Agent 改写。
- 合并或删除笔记。
- 将外部知识或回顾结果写入知识库。
- 创建任务。
- 激活、修正或撤销长期记忆。

### 6.5 编辑与版本

笔记有两条编辑路径：

1. **人工重写**：用户直接修改并保存，生成新版本。
2. **Agent 辅助编辑**：Agent 生成修改预览和差异，用户确认后保存为新版本。

两条路径都必须保留版本历史。系统记录修改者、修改时间和来源；Agent 编辑还应记录使用的操作类型或指令摘要。搜索和问答默认使用最新有效版本，历史引用仍能定位到当时版本。

### 6.6 记录状态

产品状态至少包括：

- `received`：原始输入已保存。
- `processing`：正在执行解析、OCR、索引或 AI 整理。
- `ready`：主要派生处理完成，可正常使用。
- `needs_attention`：存在需要用户确认或补充的信息。
- `processing_failed`：派生处理失败，原始输入仍可用且可以重试。

底层可保留更细的索引和导入状态，但用户界面应聚合为清晰、可恢复的状态。

## 7. 第二阶段：理解

### 7.1 知识库问答

- 默认只使用当前用户的有效笔记版本回答。
- 回答必须展示引用的笔记、版本和可定位片段。
- 证据不足、证据门禁未通过或引用不一致时，系统明确拒答或说明限制。
- 系统不得用模型常识补全并声称这是用户曾经记录的内容。

### 7.2 阅读时洞察

- 用户打开单条笔记后，可主动点击“洞察”。
- 系统不得在日常阅读中自动弹出深度推理结果。
- 洞察可包括相关笔记、主题演变、相似或矛盾观点、知识缺口和可继续追问的问题。
- 洞察必须展示使用的个人笔记来源。

### 7.3 外部知识

- 默认关闭外部知识检索。
- 用户在对话中明确要求“结合外部资料”“查询最新信息”等时，才允许调用外部知识能力。
- 回答分为“来自我的笔记”“来自外部资料”和“Agent 综合判断”。
- 外部来源应带可访问引用。
- 外部内容不会自动写回知识库；用户可要求生成候选笔记并确认保存。

## 8. 第三阶段：行动

### 8.1 轻量任务模型

任务至少包含：

- 标题。
- 状态：`todo`、`in_progress`、`done`、`cancelled`。
- 可选截止日期。
- 创建入口。
- 来源笔记、来源对话或来源回顾。
- 创建时间、更新时间和完成时间。

首版不包含提醒投递、重复任务、负责人、日历、项目状态和复杂依赖。

### 8.2 创建入口

任务可通过以下入口创建：

- 笔记自动识别行动候选，经确认后创建。
- Web Agent 对话中明确提出，经确认后创建。
- 微信 Agent 对话中明确提出，经确认后创建。
- 任务中心手动创建。
- 回顾报告中的行动项，经确认后创建。

### 8.3 候选与任务状态

行动候选状态：

> proposed → confirmed | dismissed | expired

确认后的任务状态：

> todo → in_progress → done | cancelled

候选不是任务，不进入正式任务列表和完成率统计。确认必须绑定候选版本、内容哈希、用户和有效期，并保持幂等。

### 8.4 微信创建任务

微信是双向轻量 Agent 入口，不只是单向采集通道。

流程：

1. 用户发送“创建任务：周五前完成搜索页原型”。
2. Agent 返回结构化候选，包括标题、可选截止时间和来源。
3. 用户回复“确认”，或用自然语言修改候选。
4. 修改后再次展示最新版候选。
5. 确认成功后创建任务并返回回执。
6. 用户在 Web 任务中心查看和管理任务。

意图不清时，Agent 询问用户是保存笔记还是创建任务，不得猜测写入。确认过期后需重新发起；重复确认不得创建重复任务。

## 9. 第四阶段：回顾

### 9.1 回顾类型

- **每日回顾**：当天笔记、关键主题、任务变化和待处理候选。
- **每周回顾**：主题演变、重要决策、未完成任务、行动趋势和知识缺口。
- **往日回声**：按时间、标签或当前上下文重新呈现旧笔记。

三种回顾都由用户主动触发，不自动调度、不主动推送。

### 9.2 生成与写回

- 回顾基于固定的数据快照生成，并标注数据截止时间。
- 回顾报告默认只读。
- 用户可确认将报告保存为新笔记。
- 用户可确认将报告中的行动项创建为任务。
- 新笔记或任务必须保存来源回顾和来源数据引用。

## 10. 微信三层记忆管理

产品中的三层记忆指完整会话记录、模型工作记忆和长期记忆。三者具有不同的事实与生命周期边界。

### 10.1 第一层：会话记录

- 保存微信原始消息、Agent 回复、确认动作和工具结果引用。
- 绑定当前用户与微信会话，长期持久且可审计。
- 原始会话不会整段注入模型。
- 微信和 Web 分别维护独立会话，不互相续接。
- 两端只共享已确认的长期记忆。

微信会话通过以下方式切分：

- 超过可配置的空闲阈值后，下一条消息创建新会话。
- 用户可发送“新对话”主动创建新会话。

空闲阈值是运行配置，不改变产品语义；首版默认值为 2 小时，并可通过真实会话评测调整。

### 10.2 第二层：大模型对话记忆

模型工作记忆只服务当前微信会话，由以下有界内容组成：

- 最近消息窗口。
- 较早消息的压缩摘要。
- 当前任务候选或长期记忆候选。
- 当前步骤必要的工具结果引用。
- 与当前问题相关的有效长期记忆。

模型工作记忆受 Token 预算约束，可从会话记录重新生成，不是长期事实来源。

用户发送“忘记刚才”时：

- 清空当前会话的压缩摘要、临时推理状态和未确认候选。
- 不删除原始会话记录。
- 不撤销长期记忆。
- Agent 返回明确的清空范围回执。

### 10.3 第三层：长期记忆

长期记忆跨微信和 Web 会话共享，用于稳定偏好、目标、事实和约束。

- 用户明确说“记住……”时，Agent 生成结构化候选。
- 候选展示规范化内容、类型和来源。
- 用户再次确认后，候选才成为有效长期记忆。
- 模型推断只能产生候选，不能直接激活。
- 修正已有记忆时创建同一事实谱系的新版本，并将旧版本标记为已替代。
- 撤销后，该记忆不再参与普通召回；历史仍保留用于审计。
- “撤销”与“永久删除”是不同操作：撤销保留版本审计；用户发起永久删除时，系统按个人数据删除流程移除正文与可识别投影。
- 长期记忆召回必须回查当前有效状态和版本。
- 密码、Token、Cookie 和服务密钥等敏感内容不得进入长期记忆。

微信支持以下自然语言操作：

- “你记得我什么？”：列出相关有效长期记忆及来源。
- “记住……”：创建候选并请求确认。
- “不是咖啡，是茶”：创建修正候选并请求确认。
- “忘掉这条”：识别目标后请求撤销确认。
- “忘记刚才”：清空当前模型工作记忆。
- “新对话”：结束当前会话并创建新会话。

Web 提供完整的长期记忆列表、状态、来源、版本历史、修正和撤销管理。

## 11. 系统边界与组件

### 11.1 渠道层

- **Web 工作台**：完整记录、管理、问答、任务和回顾界面。
- **微信适配器**：账号绑定、消息验签、去重、会话切分、消息路由和回执。

### 11.2 应用与领域层

- **输入路由**：区分笔记、任务、记忆、普通对话和回顾意图。
- **确认网关**：统一校验用户、动作类型、候选版本、内容哈希、有效期和幂等键。
- **笔记服务**：管理原文、版本、标签、附件和删除。
- **任务服务**：管理行动候选、任务、状态和来源。
- **Agent Runtime**：执行问答、洞察、外部知识编排和编辑提案。
- **上下文组装器**：按 Token 预算组装当前消息、摘要和长期记忆。
- **Memory 服务**：管理长期记忆候选、状态、版本、冲突和召回。
- **回顾 Workflow**：生成每日、每周和往日回声报告。
- **导入处理器**：处理文件、OCR、网页正文和派生数据。
- **观察与审计**：记录有界事件、失败、来源、模型版本和确认动作。

各组件通过明确接口沟通。模型不能直接访问数据库、对象存储或向量数据库，也不能自行构造可信用户范围。

### 11.3 数据与外部能力

- **MySQL**：用户、笔记版本、标签、任务、确认记录、回顾快照和长期记忆的事实源。
- **RAG**：笔记和长期记忆的可重建搜索投影，不决定业务事实是否有效。
- **对象存储**：保存原始文件、图片和派生文本引用。
- **外部知识检索**：只在用户明确要求时启用，默认只读。

所有查询和写入的用户范围只来自 Web 登录会话或微信账号绑定。客户端参数、导入内容和模型输出不能覆盖用户身份。

## 12. Agent 权限模型

### 12.1 可自动执行的动作

- 检索个人笔记和已授权长期记忆。
- 生成摘要、标题、AI 标签和弱关联。
- 生成阅读洞察。
- 生成编辑提案、行动候选和长期记忆候选。
- 生成只读回顾报告。
- 在用户明确要求时读取外部知识。

### 12.2 必须确认的动作

- 应用 Agent 改写。
- 合并或删除笔记。
- 创建任务。
- 激活、修正或撤销长期记忆。
- 将外部知识或回顾报告保存为笔记。

确认动作必须通过领域服务提交，具备权限、版本、哈希、有效期和幂等保护。

## 13. 异常处理与恢复

### 13.1 通用原则

- 原始输入成功保存后，不得因 OCR、索引、模型或外部服务失败而丢失。
- 事实写入与派生处理分离。
- 派生处理可重试，事实写入必须幂等。
- 用户看到明确状态、影响范围和下一步操作，而不是内部错误细节。

### 13.2 关键场景

| 场景 | 系统行为 | 用户反馈 |
|---|---|---|
| 微信重复投递 | 按可信消息 ID 去重 | 只生成一条笔记、候选或任务 |
| 文件或 OCR 失败 | 保留原文件，派生任务可重试 | 原文件已保存，正文提取失败 |
| RAG 索引失败 | 笔记事实不回滚，投影后台重试 | 内容可读可编辑，暂不可语义检索 |
| 回答证据不足 | 停止有根据回答 | 说明未找到依据并建议调整问题 |
| 候选已过期 | 拒绝陈旧确认并重新提取 | 内容已变化，请确认最新版 |
| 回顾生成时数据变化 | 固定快照，必要时最多重建一次 | 标明数据截止时间 |
| 外部知识不可用 | 保留个人笔记结果 | 单独说明外部资料获取失败 |
| 服务重启 | 从事实记录和耐久等待恢复 | 不要求用户重复已成功写入的动作 |

## 14. 隐私与可信体验

- 用户原文、AI 派生内容和外部资料在存储与界面中明确区分。
- 模型只接收当前任务所需的有界上下文。
- 日志、事件和指标不记录正文、Cookie、Token、密码或服务密钥。
- 跨用户资源统一返回不存在或等价结果，避免泄露资源存在性。
- 用户可以查看、导出、修正、撤销和彻底删除属于自己的数据。
- 提示注入内容只能作为不可信数据，不能提升为系统指令。
- Web 使用状态卡、版本差异和重试按钮反馈；微信使用简短回执和可回复动作反馈。
- Web 与微信共享同一业务状态，不各自维护事实副本。

## 15. 分阶段交付

采用按能力阶段纵向建设的方案。上一阶段的正确性、可恢复性和可信性门禁未通过前，不开启下一阶段的自动化能力。

本文件是跨阶段产品范围规格，不对应一个超大型实施计划。四个阶段分别形成独立的实施计划、验收和发布门禁；首先只为阶段 1 编写实施计划。后续阶段在上一阶段通过验收后再规划，避免并行扩张需求范围。

微信原始会话记录和有界对话上下文是阶段 1 渠道接入与阶段 3 任务确认的基础设施，按实际依赖提前交付；阶段 4 交付的是面向用户的完整三层记忆管理，尤其是长期记忆候选、跨会话召回、修正、撤销和 Web 管理界面。

### 阶段 1：记录可信

范围：Web 与微信输入、文件/图片/链接、收集箱、多级标签、版本化编辑和低风险 AI 整理。

出口标准：

- 输入不丢失。
- 重复投递不新增。
- 失败可恢复。
- AI 整理可识别、可修改、可撤销。

### 阶段 2：理解可信

范围：有来源问答、阅读时主动洞察、按用户指令结合外部知识。

出口标准：

- 引用可定位具体笔记版本。
- 证据不足时可靠拒答。
- 个人笔记、外部知识和 Agent 判断不混淆。

### 阶段 3：行动可控

范围：行动候选、Web/微信对话创建、手动创建、轻量任务中心和来源追溯。

出口标准：

- 未确认不创建任务。
- 重复确认保持幂等。
- 任务状态转换合法。
- 任务来源可回看。

### 阶段 4：闭环成立

范围：每日回顾、每周回顾、往日回声、三层记忆的完整管理和回顾结果写回。

出口标准：

- 回顾快照一致且标明截止时间。
- 长期记忆经过审核并可修正、撤销。
- 回顾报告可转为笔记或任务并保留来源。
- 完整路径“记录 → 理解 → 行动 → 回顾 → 新记录”通过端到端验证。

每个阶段使用功能开关灰度启用，并保留回滚能力。

## 16. 测试与验收策略

### 16.1 发布前：功能闭环可用且 Agent 值得信任

- **单元测试**：状态机、权限、版本、幂等、上下文预算、候选过期和冲突策略。
- **集成测试**：MySQL、对象存储、RAG、微信回调、异步处理和确认恢复。
- **端到端测试**：记录 → 问答 → 任务 → 回顾 → 写回。
- **Agent 评测**：意图路由、引用一致性、候选准确性、外部知识分区和可靠拒答。
- **安全测试**：跨用户隔离、提示注入、敏感信息、陈旧确认和伪造微信消息。
- **故障测试**：模型、RAG、OCR、微信重试、SSE 断线和服务重启。

### 16.2 上线后：验证使用习惯是否形成

首轮小规模试用先建立基线，再为后续阶段设目标值。观察指标包括：

- 记录：周活跃记录者、微信输入成功率、7 日和 30 日持续记录。
- 理解：有来源问答成功率、洞察触发率、拒答后的改问率。
- 行动：候选确认率、任务完成率、误创建和撤销率。
- 回顾：每日与每周回顾主动触发率、报告写回率。
- 信任：AI 整理撤销率、长期记忆修正率和用户报告的数据问题。

指标不得记录个人正文或敏感信息。

## 17. 验收场景

### 场景一：微信记录到可靠问答

1. 用户通过微信发送一段文字和一张图片。
2. 系统只创建一条输入记录并保存原始内容。
3. OCR 成功后，AI 标题和标签明确标记为派生内容。
4. 用户在 Web 中询问相关问题。
5. 回答引用该笔记的当前版本和对应片段。

### 场景二：微信对话创建任务

1. 用户在微信中明确要求创建带截止日期的任务。
2. Agent 返回结构化任务候选。
3. 用户修改截止日期并确认最新版候选。
4. 系统只创建一个任务。
5. 用户可在 Web 任务中心查看任务及来源对话。

### 场景三：长期记忆修正

1. 用户发送“记住我喜欢咖啡”。
2. Agent 返回长期记忆候选，用户确认后激活。
3. 后续用户发送“不是咖啡，是茶”。
4. Agent 展示旧值与修正候选。
5. 用户确认后，新版本生效，旧版本保留为已替代且不再召回。

### 场景四：主动回顾写回

1. 用户主动发起每周回顾。
2. 系统基于固定快照生成带来源的只读报告。
3. 用户选择一条结论保存为笔记，并将一条行动创建为任务。
4. 新笔记和任务均保留来源回顾及原始数据引用。

### 场景五：失败不丢数据

1. 用户导入 PDF，随后 OCR 或 RAG 服务不可用。
2. 原始文件和笔记事实仍可访问。
3. 系统展示失败范围和重试入口。
4. 依赖恢复后只重试失败的派生处理，不重复创建笔记。
